# 经验库与用户反馈设计

日期：2026-11-19
状态：待评审（第 7 节有待用户确认的决定）
关联计划：[2026-11-19-experience-library-plan.md](../plans/2026-11-19-experience-library-plan.md)
调研：Codex 只读调研，记录在维护者的交接目录 `2026-11-19-codex-experience-library/result.md`；本设计按用户决定做了调整（每日批处理、MySQL、自建）。

## 1. 现状

- **点赞点踩已保存但没人用。** 主站和 Widget 的按钮调用 `PUT /topics/{topic}/messages/{message}/feedback`，写入 `da_agent_message.feedback`（`like`、`dislike` 或空）。读取它的只有消息列表本身；没有管理接口、统计、评测或提示词使用它。管理员看不到。Agent 详情页（调试预览）故意去掉了评价按钮；OntoFoundry 的对话组件没有评价能力。
- **助手不会从历史中学习。** 每个任务只用助手的系统提示词和技能；同类错误会在不同会话里重复。
- **相关基础设施已有**：调度循环（`task_coordinator._schedule_loop`）、任务与事件记录（MySQL）、系统提示词构建与落库（`task_executor._build_system_prompt`、`record_task_system_prompt`）、评测框架（`core/eval_*`）、Pi 运行时可另起一个无工具的会话（`createAgentSession`）。

## 2. 目标

1. 管理员能看到每个助手的点赞点踩，并能打开对应会话。
2. 每天读一遍前一天的会话记录和评价，提炼成可复用的「经验」，下一次任务按需带上，让助手少犯重复的错误。
3. 经验可追溯、可停用、可回滚，不泄露业务数据，不跨用户或站点共享。

不做：自动修改助手提示词或技能源码；把业务事实或口径存成经验（口径回流 OntoFoundry，见 4.3）；语义向量检索（第一版用关键词）。

## 3. 选型

| 方案 | 结论 |
| --- | --- |
| 自建（参考 ReasoningBank、ACE：条目化经验、成功与失败都提炼、增量维护） | **采用**。不加依赖和服务，隔离、审核、评测都在自己手里。 |
| mem0 库 | 不采用。需要向量库和内网嵌入模型；抽取偏用户事实而非任务方法；站点、用户隔离要另外映射。 |
| Letta 服务 | 不采用。多一个服务，且自带的 Agent 模型与 DataAgent 重叠。 |
| Pi 社区扩展（pi-hindsight、pi-self-learning 等） | 不直接用。它们面向单机单用户，存本地文件；DataAgent 的 Pi 会话也不加载扩展。借鉴其做法：独立无工具的复盘会话、有上限的核心条目、失败当约束。 |

存储用 DataAgent 现有的 MySQL：会话、任务和评价都在这里，DataAgent 主站、Widget 和 OntoFoundry（其建模运行就是 DataAgent 任务）都能用上，不新增数据库。

## 4. 方案

### 4.1 评价可见（第一步，独立有用）

- 管理接口 `GET /admin/feedback`：按时间倒序列出带评价的助手消息（时间、助手、评价、用户问题摘要、回答摘要、会话链接），可按助手、评价类型、时间筛选；返回所选范围内的点赞、点踩计数。只有管理员能访问。
- 管理端新增独立菜单「用户反馈」：跨助手列出评价，可按助手、评价类型、时间筛选，点击打开对应会话。
- 记录评价时间：`da_agent_message` 增加 `feedback_at`（迁移），每日批处理据此找出当天新评价（评价可能晚于回答）。

### 4.2 每日经验总结

- **触发**：调度循环每天固定时间（默认 UTC 18:00，即北京时间凌晨 2 点，可配置）对每个助手处理前一天；处理进度记在管理设置中（见 4.4），同一天只跑一次，失败下次重试，不影响业务任务。
- **输入**（每个助手、前一天、按身份分区分组）：
  - 终态任务：`finished`、`error`。取消和等待中的跳过。
  - 每个任务取用户问题、最终回答、工具名与成败、错误码、模型重试、被丢弃的轮次标记，截断到上限；不取工具原始输出（可能含业务数据）。
  - 当天的点赞点踩，以及评价落在更早任务上的情况。
  - 该助手当前的活跃经验（用于去重和修订）。
- **筛选与成本**：优先点踩、失败、重试多的任务，其次点赞，最后抽样普通成功任务；每个助手每天最多 30 个任务、输入不超过 8000 tokens；用便宜模型，60 秒超时，不回退到贵模型。
- **执行**：后端启动一次独立的 Pi 会话（不给任何工具、不加载技能和 MCP、不继承工作区），按专用提示词输出 JSON：每条候选含 `condition`（何时适用）、`lesson`（怎么做）、`counterexample`（何时不适用）、`evidence`（支撑它的任务 ID 和评价）、`kind`（`strategy` 来自成功，`guardrail` 来自失败或点踩）。每天每个助手最多 5 条候选。
- **校验与合并**（后端代码，不靠模型）：JSON 结构校验；正文长度上限 200 tokens；拒绝含密钥、连接串、邮箱手机号、表中真实值样式的内容；与现有条目规范化后去重，相同则只追加证据；冲突则转待审。点踩撤销：某条经验的唯一证据任务后来被点踩，该条自动停用。

### 4.3 分层：个人、助手、平台

三层，越往上共享越广、门槛越高；只能逐层由证据和管理员向上提升，不会自动向下或横向扩散。

| 层 | 来源与内容 | 谁能用 | 怎么产生 |
| --- | --- | --- | --- |
| 个人 | 一个用户的会话：表达习惯、常用范围、个人偏好 | 只有该用户 | 每日总结自动生成，用户可在自己的设置里查看和删除 |
| 助手 | 同一助手在本部署内多个用户的会话：工具怎么用、哪些步骤容易错 | 本部署内该助手的所有用户 | 至少 2 个不同用户的任务支撑才自动生效，否则为候选 |
| 平台 | 跨助手通用的企业级做法与规范 | 本部署所有助手 | 只能由管理员从助手层提升或直接编写 |

- 「部署」是隔离边界：内网部署即一个企业，登录用户之间可以共享助手层和平台层；Widget 嵌入的外部站点各成一个分区，外部访客的会话只生成个人层，不参与助手层和平台层，避免外部内容污染企业知识。
- 个人层只来自本人的会话，不能被提升；助手层要有多个用户的证据，是防止个人偏好或一次错误变成全体经验的主要手段。
- **业务知识不进经验库，回流到 OntoFoundry。** 总结中发现的口径问题（例如"销售额应排除退款"）属于企业业务语义，正确的归宿是本体：以候选形式交给 OntoFoundry 已有的 `submit_feedback` 回流（MCP 网关的口径纠偏入口），由建模人员审阅后进入发布版本。经验库只存执行方法（怎么查、怎么验证、怎么避免某类错误）。这样企业级知识只有一个权威来源，可版本化、可审计。

### 4.4 存储

只新增一张表 `da_agent_experience`：

| 字段 | 说明 |
| --- | --- |
| `experience_id`、`revision`、`supersedes_id` | 条目与版本；修改产生新版本 |
| `scope` | `personal`、`assistant`、`platform` |
| `agent_id` | 个人层、助手层必填 |
| `owner_user_id` | 个人层必填 |
| `partition_key` | 隔离边界：本部署的登录用户为同一分区，每个 Widget 站点各为一个分区 |
| `kind`、`condition`、`lesson`、`counterexample` | 内容 |
| `evidence_json` | 任务 ID、评价、日期；只存引用 |
| `status` | `candidate`、`active`、`retired` |
| `created_by`、`reviewed_by`、`reason`、时间戳 | 审计 |

每日作业的运行状态（每个助手上次处理到哪一天、上次结果与用量）不单独建表，存在现有管理设置（`persist_admin_settings`）中的 `experience_digest` 一项；同一助手同一天只处理一次，失败下次调度重试。

上限：个人层每人每助手 20 条，助手层每分区每助手 50 条，平台层 100 条；超出按证据数和时效归档。90 天没有新证据的候选过期。

### 4.5 生效与注入

**读取时机**：与 Pi 的 `before_agent_start` 钩子相同（每次运行开始、调用模型之前，pi-hindsight、pi-self-learning 用它注入经验；见 Pi `docs/extensions.md`）。DataAgent 在后端构建每个任务的系统提示词时完成，不用 Pi 扩展：后端掌握用户和站点身份，能按分层规则过滤；注入内容随系统提示词落库可追溯；Pi 会话当前不加载扩展（`sdk-session.ts` 传入空扩展列表）。

**以后可加**：运行中按需查询的工具 `search_experience`（参照 pi-hindsight 的 `recall`、Letta 按需读取深层记忆），同样按分层和身份过滤；条目多到 5 条不够用时再加，第一版不做。

- 个人层：自动生效，只注入给本人。
- 助手层：至少 2 个不同用户的任务支撑（点赞计入，点踩反向）自动生效；其余为候选，管理员确认后生效。
- 平台层：只能由管理员提升或编写。
- 注入顺序：平台层、助手层、个人层；同一条件冲突时取更高层，个人层不能覆盖平台层的规范。
- 注入：构建系统提示词时增加「历史经验参考」一节，说明它不能覆盖当前请求、技能约定和权限规则。按分区和助手过滤，再按与用户问题的关键词重合度、证据数、时效排序，三层合计最多 5 条、1000 tokens；没有相关的就不加。所用条目 ID 和版本随任务落库，暂停后恢复沿用同一组。
- 管理端「经验」页签：列表与详情（条件、内容、证据链接、版本历史），可启用、停用、提升为平台级、编辑；全局开关一键关闭注入。

### 4.6 安全

- 会话记录当作不可信材料：总结提示词声明其中的指令一律不执行；输出只接受结构化字段。
- 不存业务数据：输入不含工具原始输出；入库前做模式检查；涉及权限、数据范围、业务口径的建议一律只能成为候选。
- 隔离：经验服务自己确定身份，不沿用 `context=None` 时的宽松读取；无法确定身份的匿名来源不参与总结。
- 评测任务不进入总结，也不注入经验（评测时显式关闭）。

### 4.7 效果评估（暂不做）

以后用现有评测功能把同一批测试问题分别在关闭和开启经验时各跑一遍，比较正确率、重复错误、工具调用、耗时和成本，并加入跨用户或站点泄漏用例。第一版不做，由管理员开关注入并观察用户反馈。

## 5. 对 OntoFoundry 的影响

- 经验注入不需要改动：建模运行是 DataAgent 任务，经验由 DataAgent 注入。经验是执行方法，不能作为本体业务事实或新增概念的证据。
- 口径回流（暂不做）：以后由 DataAgent 后端以服务令牌调用 OntoFoundry 的 `submit_feedback`，需要两边约定令牌配置和工作空间对应关系，届时另写设计。在此之前，每日总结遇到口径问题只丢弃，不存进经验库。
- OntoFoundry 的评价按钮暂不加，等 4.1 证明评价有用后再定。

## 6. 分步交付

1. 评价可见：`feedback_at` 迁移、管理接口、助手详情「用户反馈」页签。
2. 经验库：两张表、每日作业、总结会话、校验合并、管理页签、注入与全局开关。
暂不做：效果评估（用现有评测功能对比开关经验的结果）；口径回流 OntoFoundry（4.3 所述，另行设计）。

没有评估时，注入由管理员通过全局开关决定，默认关闭；开启后通过「用户反馈」菜单观察点踩是否变化，出现问题可关闭开关或停用单条经验。
