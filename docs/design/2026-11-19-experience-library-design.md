# 经验库与用户反馈设计

日期：2026-11-19
状态：待评审（第 7 节有待用户确认的决定）
关联计划：[2026-11-19-experience-library-plan.md](../plans/2026-11-19-experience-library-plan.md)
调研：Codex 只读调研，记录在维护者的交接目录 `2026-11-19-codex-experience-library/result.md`；本设计按用户决定做了调整（每日批处理、MySQL、自建）。

## 1. 现状

- **点赞点踩已保存但没人用。** 主站和 Widget 的按钮调用 `PUT /topics/{topic}/messages/{message}/feedback`，写入 `da_agent_message.feedback`（`like`、`dislike` 或空）。读取它的只有消息列表本身；没有管理接口、统计、评测或提示词使用它。管理员看不到。Agent 详情页（调试预览）故意去掉了评价按钮；OntoFoundry 的对话组件没有评价能力。
- **助手不会从历史中学习。** 每个任务只用助手的系统提示词和技能；同类错误会在不同会话里重复。
- **相关基础设施已有**：调度循环（`task_coordinator._schedule_loop`）、任务与事件记录（MySQL）、系统提示词构建与落库（`task_executor._build_system_prompt`、`record_task_system_prompt`）、评测框架（`core/eval_*`）、Pi 运行时可另起一个无工具的会话（`createAgentSession`）。

## 2. 目标

1. 管理员能看到每个助手的点赞点踩，并能打开对应会话。
2. 每天读一遍前一天的会话记录和评价，提炼成可复用的「经验」，下一次任务按需带上，让助手少犯重复的错误。
3. 经验可追溯、可停用、可回滚，不泄露业务数据，不跨用户或站点共享。

不做：自动修改助手提示词或技能源码；把业务事实或口径存成经验（口径回流 OntoFoundry，见 4.3）；语义向量检索（第一版用关键词）。

## 3. 选型

| 方案 | 结论 |
| --- | --- |
| 自建（参考 ReasoningBank、ACE：条目化经验、成功与失败都提炼、增量维护） | **采用**。不加依赖和服务，隔离、审核、评测都在自己手里。 |
| mem0 库 | 不采用。需要向量库和内网嵌入模型；抽取偏用户事实而非任务方法；站点、用户隔离要另外映射。 |
| Letta 服务 | 不采用。多一个服务，且自带的 Agent 模型与 DataAgent 重叠。 |
| Pi 社区扩展（pi-hindsight、pi-self-learning 等） | 不直接用。它们面向单机单用户，存本地文件；DataAgent 的 Pi 会话也不加载扩展。借鉴其做法：独立无工具的复盘会话、有上限的核心条目、失败当约束。 |

存储用 DataAgent 现有的 MySQL：会话、任务和评价都在这里，DataAgent 主站、Widget 和 OntoFoundry（其建模运行就是 DataAgent 任务）都能用上，不新增数据库。

## 4. 方案

### 4.1 评价可见（第一步，独立有用）

- 管理接口 `GET /admin/feedback`：按时间倒序列出带评价的助手消息（时间、助手、评价、用户问题摘要、回答摘要、会话链接），可按助手、评价类型、时间筛选；返回所选范围内的点赞、点踩计数。只有管理员能访问。
- 管理端新增独立菜单「用户反馈」：跨助手列出评价，可按助手、评价类型、时间筛选，点击打开对应会话。
- 记录评价时间：`da_agent_message` 增加 `feedback_at`（迁移），每日批处理据此找出当天新评价（评价可能晚于回答）。

### 4.2 身份与分区（谁的会话可以参与）

身份从会话表 `da_agent_topic` 的 `source`、`website_id`、`auth_user_id`、`external_user_id` 读取，不用执行时合并后的 `_execution_user_id`（它把主站用户和 Widget 外部用户合成一个字符串，`local:admin` 可能撞上主站管理员）。

| 会话来源 | 身份是否可信 | 分区 `partition_key` | 参与 |
| --- | --- | --- | --- |
| 主站已登录用户（`source=web` 且 `auth_user_id` 非空） | 可信 | `web` | 个人层、助手层计数 |
| 开启服务端接入的 Widget 站点（`server_side.enabled`，如 OntoFoundry） | 可信（宿主持密钥上报用户） | `site:<website_id>` | 个人层、助手层计数 |
| 普通浏览器 Widget 站点、匿名主站会话 | 不可信（用户 ID 是浏览器明文请求头） | — | 不生成、也不注入经验 |
| 管理端调试预览（`is_agent_preview=1`）、评测会话 | — | — | 排除 |

- 个人层按 `(partition_key, owner_user_id)` 隔离；助手层按 `(partition_key, agent_id)`；自动生成的内容从不跨分区。
- 平台层只由管理员编写或提升，管理员选择它适用的分区（默认全部可信分区）；这是企业级知识跨分区共享的唯一途径。
- 「2 个不同用户」由后端按证据任务 ID 反查会话归属来计数，不采信模型输出的任何用户信息。
- 评测会话目前没有标记字段；评测功能接入经验时需先在会话上加标记（属于暂不做的效果评估）。

### 4.3 每日经验总结

- **触发与进度**：独立的后台协程每天固定时间（默认 UTC 18:00，即北京时间凌晨 2 点，可配置）运行，不放进 `_schedule_loop`（它的锁 60 秒无续期，且会阻塞到期的定时消息）。用 Redis 锁（持有期间续期）保证只有一个实例在跑；每个 `(agent_id, partition_key)` 处理到哪一天记在 Redis（DataAgent 的 Redis 开启了持久化），从上次成功日的次日逐日补跑到昨天，最多回溯 7 天。不使用管理设置存进度：它只保存固定白名单键，且整行覆盖写，会与管理员保存设置互相覆盖。
- **输入**（按分区、助手分组，只含可信身份的会话）：
  - 终态任务：`finished`、`error`。取消和等待中的跳过。
  - 用户问题；最终回答先剥离 `chart_spec`、代码块、Markdown 表格和连续数字后再截断，避免查询结果进入总结；工具名与成败；失败或被拒的工具调用取工具名、脚本或子命令和脱敏后的首行错误类型（不含结果行）；错误码、模型重试、被丢弃的轮次。
  - 新评价：`feedback_at` 落在处理日内的点赞、点踩、取消评价，包括落在更早任务上的。
  - 该分区该助手当前的活跃经验（去重与修订用）。
- **筛选与成本**：优先点踩、失败、重试多的任务，其次点赞，再抽样普通成功任务；每人每天最多 5 个任务入选，每个助手每天最多 30 个，输入不超过 8000 tokens；60 秒超时，不回退到贵模型。
- **执行**：后端直接用现有的 `request_model_text`（与 `followup_suggestions` 相同的单轮无工具调用）请求便宜模型输出 JSON，不改动 Pi 运行时。个人层按用户分别调用，只看该用户自己的任务，避免一个用户的会话影响他人的个人层；助手层对分区内的多用户任务调用一次。每条候选含 `condition`、`lesson`、`counterexample`、`evidence`（任务 ID）、`kind`（`strategy` 来自成功，`guardrail` 来自失败或点踩），每次最多 5 条。
- **校验与合并**（后端代码，不靠模型）：JSON 结构校验；正文上限 200 tokens；拒绝含密钥、连接串、邮箱手机号、表中真实值样式的内容；`evidence` 中的任务必须在本次输入内且归属正确（个人层全部属于该用户）；与现有条目规范化后去重，相同则合并证据。
- **评价变化时重算**：任一证据任务被点踩或取消点赞时，重算剩余有效证据的不同用户数：助手层不足 2 人退回候选，个人层没有有效证据则停用。

### 4.4 分层：个人、助手、平台

三层，越往上共享越广、门槛越高；只能由证据和管理员向上提升，不会自动向下或横向扩散。

| 层 | 来源与内容 | 谁能用 | 怎么产生 |
| --- | --- | --- | --- |
| 个人 | 一个可信用户自己的会话：表达习惯、常用范围、偏好 | 只有该用户 | 每日总结自动生成（第一版不做用户自管页面，管理员可在经验页查看和停用） |
| 助手 | 同一分区内该助手多个用户的会话：工具怎么用、哪些步骤容易错 | 同分区内该助手的所有用户 | 至少 2 个不同用户的任务支撑才自动生效，否则为候选 |
| 平台 | 跨助手通用的企业级做法与规范 | 管理员所选分区的所有助手 | 只能由管理员从助手层提升或直接编写 |

- 个人层不能被提升；助手层要有多个用户的证据，是防止个人偏好或一次错误变成全体经验的主要手段。
- **业务知识不进经验库。** 口径问题（例如"销售额应排除退款"）属于企业业务语义，归宿是 OntoFoundry 本体，以后经其 `submit_feedback` 回流（暂不做，见第 5 节）；在此之前总结遇到口径问题直接丢弃。经验库只存执行方法（怎么查、怎么验证、怎么避免某类错误）。

### 4.5 存储

只新增一张表 `da_agent_experience`：

| 字段 | 说明 |
| --- | --- |
| `experience_id` | 条目 |
| `scope` | `personal`、`assistant`、`platform` |
| `agent_id` | 个人层、助手层必填 |
| `owner_user_id` | 个人层必填 |
| `partition_key` | 个人层、助手层必填；平台层存所选分区列表（JSON，空表示全部可信分区） |
| `kind`、`condition`、`lesson`、`counterexample` | 内容 |
| `evidence_json` | 任务 ID、用户、评价、日期；只存引用 |
| `status` | `candidate`、`active`、`retired` |
| `created_by`、`updated_by`、`reason`、时间戳 | 审计；第一版原地更新，不做版本链 |

上限：个人层每人每助手 20 条，助手层每分区每助手 50 条，平台层 100 条；超出按证据数和时效归档。90 天没有新证据的候选过期。

### 4.6 生效与注入

**读取时机**：与 Pi 的 `before_agent_start` 钩子相同（每次运行开始、调用模型之前，pi-hindsight、pi-self-learning 用它注入经验；见 Pi `docs/extensions.md`）。DataAgent 在后端构建每个任务的系统提示词时完成，不用 Pi 扩展：后端掌握用户和站点身份，能按分层规则过滤；注入内容随系统提示词落库可追溯；Pi 会话当前不加载扩展（`sdk-session.ts` 传入空扩展列表）。

**以后可加**：运行中按需查询的工具 `search_experience`（参照 pi-hindsight 的 `recall`、Letta 按需读取深层记忆），同样按分层和身份过滤；第一版不做。

- 个人层：自动生效，只注入给本人。助手层：2 个不同用户支撑自动生效，其余候选待管理员确认。平台层：管理员提升或编写。
- 选取：按分区、助手、用户过滤后，按与用户问题的重合度、证据数、时效排序，三层合计最多 5 条、1000 tokens，没有相关的就不加。重合度用 ASCII 标识符（表名、字段名、工具名）加去停用词后的中文二字、三字片段计算，命中低于门槛的不注入。
- 呈现：「历史经验参考」一节按平台、助手、个人分小节，说明出现矛盾时以更高层为准，且都不能覆盖当前请求、技能约定和权限规则。不在代码里判断自由文本条件是否冲突。
- 暂停与恢复：首段选中的条目（ID 和渲染文本）存入任务检查点 `checkpoint.state["injected_experiences"]`，恢复时直接复用，不重新检索，前后分段提示词一致。
- 管理端「经验」页签：列表与详情（条件、内容、证据链接、审计信息），可启用、停用、提升为平台层、编辑；全局开关一键关闭注入。全局开关存在管理设置中（需把该键加入设置白名单）。

### 4.7 安全

- 会话记录当作不可信材料：总结提示词声明其中的指令一律不执行；只接受结构化字段，证据归属由代码核对。
- 不存业务数据：输入剥离工具原始输出和回答中的表格、图表数据、数字；入库前做模式检查；涉及权限、数据范围、业务口径的建议一律只能成为候选。
- 隔离：见 4.2；普通浏览器 Widget 和匿名会话不参与；调试预览排除。
- 单人刷量：每人每天最多 5 个任务入选，助手层要求不同用户。

### 4.8 效果评估（暂不做）

以后用现有评测功能把同一批测试问题分别在关闭和开启经验时各跑一遍，比较正确率、重复错误、工具调用、耗时和成本，并加入跨用户或站点泄漏用例。第一版不做，由管理员开关注入并观察用户反馈。

## 5. 对 OntoFoundry 的影响

- 经验注入不需要改动：建模运行是 DataAgent 任务，经验由 DataAgent 注入。经验是执行方法，不能作为本体业务事实或新增概念的证据。
- 口径回流（暂不做）：以后由 DataAgent 后端以服务令牌调用 OntoFoundry 的 `submit_feedback`，需要两边约定令牌配置和工作空间对应关系，届时另写设计。在此之前，每日总结遇到口径问题只丢弃，不存进经验库。
- OntoFoundry 的评价按钮暂不加，等 4.1 证明评价有用后再定。

## 6. 分步交付

1. 评价可见：`feedback_at` 迁移（任何评价变更都更新，含取消）、管理接口、独立菜单「用户反馈」。
2. 经验库：一张表、每日后台作业（Redis 锁与进度）、总结调用、校验合并、管理页签、注入与全局开关。
暂不做：效果评估（用现有评测功能对比开关经验的结果）；口径回流 OntoFoundry（4.4 所述，另行设计）。

没有评估时，注入由管理员通过全局开关决定，默认关闭；开启后通过「用户反馈」菜单观察点踩是否变化，出现问题可关闭开关或停用单条经验。
